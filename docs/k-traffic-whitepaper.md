## 1. 개요

K-Traffic은 고팡(Gopang) 생태계 위에서 동작하는 **AI 기반 교통·물류 통합 플랫폼**이다. 우버나 카카오택시처럼 새로운 차량을 수요에 맞춰 배차하는 방식이 아니라, **이미 이동 중이거나 이동 예정인 차량의 동선에 새로운 수요를 끼워 넣는** 방식으로 작동한다.

모든 등록 차량에는 **고팡 블랙박스**가 탑재되어 1분 단위로 위치·동선·목적지를 **Openhash 계층 네트워크**에 전송한다. AI 매칭 엔진(DeepSeek V3)은 이 실시간 데이터를 분석하여 신규 수요에 가장 적합한 차량 또는 차량의 조합을 선정하고, 선정된 운전자에게 수령 장소·전달 장소·인수인계 지점을 자동으로 안내한다.

모든 거래 기록은 양측의 **PDV(Personal Data Vault)**에 암호화 저장되며, 결제는 **GDC(Gopang Digital Currency)**로 서비스 완료 즉시 자동 이체된다. 별도의 현금이나 카드 거래가 없고, PDV 기록은 분쟁 발생 시 위변조 불가 증거로 활용된다.

### 핵심 가치 명제

| 속성 | 내용 |
|------|------|
| **매칭 방식** | 동선 겹침 기반 — 빈 차를 별도 파견하지 않음 |
| **신원 인증** | 고팡 PDV 양측 상호 확인 (차량·이용자 모두) |
| **거래 기록** | 양측 PDV 암호화 저장 — 위변조 불가 |
| **결제** | GDC 자동 이체 — 현금·카드 불필요 |
| **릴레이** | 장거리는 복수 차량 인수인계 조합 |
| **서버 효율** | Openhash 계층으로 로컬 수요는 로컬에서만 처리 |

## 2. 문제 정의

### 2.1 기존 교통·물류 서비스의 한계

현재의 차량 호출 서비스(우버, 카카오택시 등)와 물류 서비스(쿠팡로켓, 택배사)는 구조적으로 다음 문제를 안고 있다.

**비효율적 차량 배차.** 수요가 발생하면 가장 가까운 유휴 차량을 배차한다. 그 차량이 어디로 향하는지는 고려하지 않는다. 이미 같은 방향으로 이동 중인 차량이 있어도 활용하지 못한다.

**신원 검증의 취약성.** 운전자와 이용자는 플랫폼이 부여한 별점과 전화번호 인증에 의존한다. 신원 위조, 별점 조작, 범죄 발생 이후 추적의 어려움이 반복된다.

**거래 기록의 중앙 집중.** 모든 이동 기록이 플랫폼 서버에만 저장된다. 당사자가 직접 자신의 기록을 보유하지 않으며, 분쟁 발생 시 플랫폼의 중재에 의존해야 한다.

**장거리 물류의 비효율.** 부산에서 서울로 화물을 보내려면 전 구간을 담당하는 전용 차량이 필요하다. 해당 구간의 일부를 지나는 수많은 차량이 활용되지 않는다.

**단편화된 서비스.** 승객 이동, 소화물, 중화물, 긴급 배송이 각기 다른 앱으로 분리되어 있다.

### 2.2 K-Traffic의 접근법

K-Traffic은 세 가지 전제에서 출발한다.

첫째, **모든 차량은 어딘가로 향하고 있다.** 이미 같은 방향으로 이동 중인 차량을 활용하면 추가 이동 비용 없이 수요를 충족할 수 있다.

둘째, **신원은 이동보다 먼저 확인되어야 한다.** 탑승 전 양측의 PDV 신원이 상호 확인되면 범죄의 동기가 사라진다.

셋째, **기록은 당사자가 직접 보유해야 한다.** PDV에 저장된 기록은 플랫폼이 아닌 당사자 본인이 소유하며, 필요 시 즉시 증거로 제출할 수 있다.

### 3.2 데이터 흐름 요약

1. 차량의 블랙박스가 1분마다 현재 위치·이동 여부·목적지·예상 경로를 해당 위치의 **L1(읍면동) Openhash 서버**에 전송한다.
2. L1 서버는 동선 정보를 집계하고, 필요 시 상위 계층(L2→L3→L4)으로 전파한다.
3. 이용자가 앱에서 이동 또는 물류 수요를 입력하면, AI 매칭 엔진이 해당 수요의 **동선 범위**를 판별하고 적합한 Openhash 계층에서 차량을 탐색한다.
4. 매칭된 차량의 운전자에게 수령·전달 지시 메시지가 전송되고, 수락 시 양측 PDV에 계약이 기록된다.
5. 서비스 완료 후 GDC가 자동 이체되고 완료 기록이 PDV에 추가된다.

## 4. 핵심 구성 요소

### 4.1 고팡 블랙박스

고팡 블랙박스는 K-Traffic에 등록된 모든 차량에 탑재되는 상시 가동 소프트웨어(또는 하드웨어 모듈)이다. 핵심 기능은 다음과 같다.

**위치 전송.** 60초마다 현재 GPS 좌표(위도·경도), 이동 속도, 방향각을 해당 위치의 L1 Openhash 서버에 전송한다.

**동선 예고.** 목적지가 설정된 경우, 예상 경로(polyline) 전체를 함께 전송한다. 목적지가 없는 경우(대기 중)는 이동 없음 상태로 전송한다.

**상태 분류.** 전송 페이로드에는 차량 상태(이동 중 / 대기 중 / 운행 종료)와 차량 유형(택시 / 자가용 / 버스 / 화물차 / 오토바이)이 포함된다.

**PDV 연동.** 탑승 시작·완료, 화물 수령·전달 이벤트 발생 시 `pdv.js`를 통해 PDV 기록을 자동으로 생성한다.

```
블랙박스 전송 페이로드 (1분 단위):
{
  vehicle_id:   "BB-042",
  type:         "화물차",
  lat:          33.4996,
  lng:          126.5312,
  speed_kmh:    67,
  heading_deg:  92,
  moving:       true,
  dest_lat:     33.5097,
  dest_lng:     126.5219,
  route_points: [[33.498, 126.519], ...],
  pdv_level:    "L1",
  timestamp:    "2026-06-03T09:28:00Z"
}
```

### 4.2 Openhash 네트워크 서버 클러스터

Openhash는 고팡 생태계의 분산 네트워크 인프라다. K-Traffic은 Openhash의 지역 계층 구조를 교통·물류 정보 전파의 기반으로 사용한다.

#### 계층 구조

| 계층 | 단위 | 역할 | 전파 조건 |
|------|------|------|----------|
| **L1** | 읍면동 | 블랙박스 직접 수신, 동선 집계 | 동선이 L1 초과 시 L2로 전파 |
| **L2** | 시군구 | L1 집계 수신, 시군구 단위 현황 | 동선이 L2 초과 시 L3로 전파 |
| **L3** | 광역시도 | L2 집계 수신, 광역 단위 현황 | 광역 간 이동 시 L4로 전파 |
| **L4** | 국가 | 전국 집계 수신 | 국제 이동 시 L5로 전파 |
| **L5** | 글로벌 | 글로벌 집계 | — |

#### 핵심 원칙: 최소 전파(Minimal Propagation)

이 원칙이 K-Traffic의 서버 효율을 결정한다.

```
수요의 동선이 읍면동(L1) 이내
  → L1에서만 탐색. L2 전달 없음.

수요의 동선이 시군구(L2) 이내
  → L1 → L2 탐색. L3 전달 없음.

수요의 동선이 광역시도(L3) 이내
  → L1 → L2 → L3 탐색.

수요의 동선이 광역 간
  → L1 → L2 → L3 → L4 탐색.
```

이 구조 덕분에 제주도 한림읍 내의 배달 수요는 한림읍 L1 서버만 부하를 받고, 서울 L4 서버는 전혀 관여하지 않는다.

#### Openhash와 고팡 ID

Openhash는 고팡 ID 백서에서 기술된 DHT(분산 해시 테이블) 기반 분산 검색 네트워크를 교통 정보에 적용한 것이다. 각 차량과 이용자는 고팡 ID로부터 파생된 IPv6 주소를 통해 Openhash 네트워크에서 식별된다. 이 IPv6 주소는 지역 코드가 인코딩되어 있어, 주소 자체에서 사용자의 대략적인 위치(읍면동 수준)를 파악할 수 있다.

### 4.3 동선 겹침 매칭 알고리즘

매칭의 핵심 로직이다. 신규 수요가 발생하면 AI 매칭 엔진은 다음 순서로 차량을 선정한다.

#### Step 1. 수요 파싱

```
입력: "제주 한경면에서 도청으로 감귤 1박스 배달"

파싱 결과:
{
  type:        "물류",
  from:        { name: "한경면", lat: 33.3547, lng: 126.1614 },
  to:          { name: "제주도청", lat: 33.4995, lng: 126.5291 },
  cargo:       { item: "감귤", qty: 1, weight_kg: 15 },
  distance_km: 32,
  scope:       "L2",   // 제주시 내
  urgent:      true
}
```

#### Step 2. 동선 범위 판별

출발지와 목적지의 L1 노드 ID가 동일하면 → L1 탐색.  
동일 시군구(L2) 내이면 → L2 탐색.  
동일 광역시도(L3) 내이면 → L3 탐색.  
광역 간이면 → L4 탐색.

#### Step 3. 차량 필터링

해당 계층의 Openhash 서버에서 다음 조건을 모두 만족하는 차량 목록을 추출한다.

- **동선 겹침**: 차량의 현재 예상 경로가 수요의 출발지 반경 2km 이내를 통과하는가
- **PDV 인증**: PDV L1 이상 인증된 차량인가
- **적재 가능**: 화물 유형·중량에 적합한 차종인가 (소화물 → 자가용 가능, 중화물 → 화물차 필수)
- **시간 가용**: 예상 도착 시간 내 수령 가능한가

#### Step 4. 우선순위 정렬

다음 기준으로 후보 차량을 점수화한다.

```
점수 = (동선 겹침 정확도 × 0.40)
     + (PDV 신뢰 점수 × 0.25)
     + (거리 효율 × 0.20)
     + (예상 소요 시간 역수 × 0.15)
```

### 4.4 릴레이 인수인계 시스템

단일 차량이 전 구간을 커버하기 어려운 장거리·광역 수요를 위한 메커니즘이다.

#### 릴레이 필요 조건

- 이동 거리 > 200km이고 단독 커버 차량 없음
- 또는 수요자가 명시적으로 릴레이 분할 요청

#### 중간 인수인계 거점

K-Traffic은 전국 36개 환승 거점을 내장하고 있다.

**고속도로 휴게소 (24개):**  
경부 — 죽전, 안성, 천안삼거리, 정안알밤, 금강, 추풍령, 황간, 옥천, 칠곡, 기흥동탄  
영동 — 여주, 횡성, 둔내, 강릉  
서해안 — 행담도, 화성, 서산, 고창고인돌  
중앙 — 수안보, 풍기, 서안동  
남해 — 덕천, 진영, 함안

**고속버스터미널 (6개):**

**물류센터 (6개):**

#### 릴레이 동작 흐름

```

  경부고속도로 동선 보유 차량 목록 추출

[릴레이 구성]

  인수인계 거점: 천안삼거리휴게소

  - BB-247: 수령 기록 (천안삼거리) + 전달 기록 (서울강남)

  BB-247: 17 GDC (구간 B)

```

### 4.5 PDV (Personal Data Vault)

PDV는 고팡 생태계의 핵심 신원·기록 인프라다. K-Traffic은 PDV를 세 가지 목적으로 사용한다.

#### 신원 인증

탑승 또는 화물 수령 전, 차량과 이용자 양측의 PDV 레벨을 상호 확인한다.

| PDV 레벨 | 인증 방법 | K-Traffic 권한 |
|----------|----------|---------------|
| **L0** | 기기 자동 인식 (IPv6) | 상담·조회 가능, 매칭 제한 |
| **L1** | 실명 인증 (얼굴 인식 또는 신분증) | 승객·운전자 매칭 가능 |
| **L2** | L1 + 생체 인증 (WebAuthn/지문) | 고가 화물·긴급 서비스 가능 |
| **L3** | L2 + 4단어 시드 복구 | 기관 감사·분쟁 증거 제출 |

**L1 미만 차량은 매칭 대상에서 자동 제외된다.** 이것이 K-Traffic의 핵심 안전 메커니즘이다.

#### 거래 기록 저장

모든 이동·물류 이벤트는 `pdv.js` 모듈을 통해 즉시 PDV에 기록된다.

```javascript
// pdv.js — 탑승 시작 기록 예시
PDV.writeRideStart({
  from:          '한경면',
  to:            '제주도청',
  driverIpv6:    '2601:a4b:...c9f0',
  vehicleNo:     '제주 12가 3456',
  confirmedGdc:  8,
})
```

PDV 기록의 구조 (5W1H):

```json
{
  "svc":          "traffic",
  "type":         "traffic_ride_start",
  "id":           "RPT-traffic-start-1748908800000",
  "content_hash": "sha256:a3f8c...",
  "who": {
    "ipv6":       "2601:a4b:...c9f0",
    "role":       "passenger",
    "counterparty": "2601:b3d:...f1a2"
  },
  "when": {
    "generated_at":  "2026-06-03T09:28:00Z",
    "period_start":  "2026-06-03T09:28:00Z",
    "period_end":    "2026-06-03T09:28:00Z"
  },
  "where": {
    "svc_url":    "https://traffic.hondi.net",
    "label":      "한경면"
  },
  "what": {
    "summary":    "탑승 시작: 한경면 → 도청 | 차량 제주12가3456",
    "from":       "한경면",
    "to":         "제주도청",
    "vehicle_no": "제주12가3456",
    "confirmed_gdc": 8
  },
  "how":  { "method": "PDV 신원 상호 확인 후 탑승" },
  "why":  { "goal": "이동 기록 보관 및 범죄·분쟁 예방" }
}
```

#### 분쟁 해결

분쟁 발생 시, 수요자와 운전자 양측의 PDV 기록이 SHA-256 해시로 무결성이 검증되고 자동으로 비교된다. 기록의 일치 여부가 판정 근거가 된다. 플랫폼의 중재 없이 당사자 간 기록이 직접 증거가 된다.

### 4.6 GDC 자동 결제 시스템

GDC(Gopang Digital Currency)는 고팡 생태계의 내부 디지털 화폐다. 1 GDC ≈ 1,000원의 가치를 가지며, 고팡 지갑 앱을 통해 충전·환전이 가능하다.

#### 요금 산정 기준

```
기본요금:  2 GDC (5km 이내)
거리 추가: 0.3 GDC / km
중량 추가: 0.1 GDC / kg (10kg 초과분)
시간대:   23:00~06:00 야간 할증 ×1.3
릴레이:   구간별 독립 산정 후 합산
```

#### 결제 흐름

```
1. 매칭 수락 시: 예상 GDC 수요자 지갑에서 에스크로 예치
2. 서비스 진행 중: GDC 잠금 상태
3. 목적지 도착 확인: 자동 이체 트리거
4. 이체 완료: 운전자 지갑에 GDC 지급
5. 양측 PDV에 결제 완료 기록
```

현금 거래나 카드 단말기가 불필요하며, 외국인이나 비현금 이용자도 제약 없이 서비스를 이용할 수 있다.

#### 수수료 구조

플랫폼 수수료는 거래 GDC의 8%이며, 이 중 절반은 Openhash 네트워크 운영 비용으로 배분된다.

### 4.7 고팡 ID · SSO 인증

K-Traffic은 고팡 생태계의 공통 인증 시스템을 사용한다. `subsystem-auth.js`를 통해 단일 로그인(SSO)이 구현되며, 모든 서브시스템(K-Traffic, K-Health, K-Law 등)이 고팡 ID 하나로 이용 가능하다.

#### 인증 흐름

```
[경로 1] GWP 토큰 처리
  hondi.net 로그인 → gwp_token 발급 → URL 파라미터 전달
  → subsystem-auth.js가 파싱 → sessionStorage 저장

[경로 2A] 세션 캐시 재사용
  기존 유효 세션 확인 → 즉시 인증 완료
  콘솔: [SSO] 경로2A 세션 캐시 ✅ 2601:xxxx

[경로 2B] Silent iframe 자동 갱신
  세션 만료 → 고팡 SSO 서버에 silent iframe 요청
  → postMessage로 신규 토큰 수신 → 재인증
  콘솔: [SSO] 경로2B Silent iframe ✅ 2601:xxxx
```

인증 완료 시 `window._onGopangAuth(user)` 콜백이 호출되며, `user.ipv6`와 `user.level`이 전달된다.

## 5. AI 매칭 엔진

### 5.1 DeepSeek V3 Pro 선택 이유

K-Traffic의 AI 매칭 엔진으로 DeepSeek V3 Pro(model: `deepseek-chat`)를 선택한 이유는 다음과 같다.

- **긴 컨텍스트 처리**: 차량 풀, 동선 데이터, 환승 거점 정보를 단일 컨텍스트에 담아 처리 가능
- **한국어 능력**: 수요자의 자연어 입력(예: "한경면에서 도청으로 감귤 1박스")을 구조화된 데이터로 정확하게 파싱
- **비용 효율**: Anthropic Claude 대비 토큰 비용이 낮아 실시간 매칭 비용 절감
- **API 호환성**: OpenAI 호환 API로 기존 Anthropic 폴백 구조와 쉽게 통합

### 5.2 시스템 프롬프트 구조

AI 매칭 엔진에는 4단계 처리 지시가 포함된 시스템 프롬프트가 주입된다.

```
STEP 1. 수요 분석
  - 유형: 이동 / 물류 / 복합
  - 출발지·목적지·경유지·화물 중량
  - 시간 조건: 즉시 / 예약
  - Openhash 범위: L1 / L2 / L3 / L4

STEP 2. 차량 탐색
  조건 A: 동선 겹침 (경로가 출발지 2km 반경 통과)
  조건 B: PDV L1 이상 인증
  조건 C: 화물 유형·중량에 적합한 차종
  조건 D: 릴레이 필요 시 인수인계 지점에서 만날 수 있는 차량 조합

STEP 3. 릴레이 조합 (장거리)
  중간 환승 거점 지정 → 차량 A·B 조합

STEP 4. 결과 제시
  수요자 요약 + 운전자별 메시지 블록
```

### 5.3 응답 형식

AI는 수요자용 자연어 요약과 운전자용 구조화 메시지를 동시에 생성한다.

```
[수요자 화면]
✅ 매칭 결과

출발: 한경면 → 도착: 제주도청 (약 32km)
탐색 레벨: Openhash L2 (제주시 내)

🚚 추천 차량 — 화물차 (PDV L1)
이○○ 님 차량, 한림읍 방면 이동 중
예상 소요: 약 50분 / 요금: 6 GDC

[운전자 메시지 블록]
┌─────────────────────────────────┐
차량: 이○○ (화물차)  PDV: L1
─────────────────────────────────
📍 수령: 제주 한경면 청수리
📦 물품: 감귤 1박스 (15kg)
🏁 전달: 제주도청 (제주시 문연로 6)
🔄 인수인계: 해당 없음
💰 보상: 6 GDC (완료 즉시 자동 이체)
🔐 PDV 기록: 수령·전달 후 자동
└─────────────────────────────────┘

수요 ID: DM-0047
탐색 레벨: L2 (제주시)
```

### 5.4 API 호출 경로

직접 API 노출을 방지하기 위해 모든 AI 호출은 `gopang-proxy` Cloudflare Worker를 경유한다.

```
클라이언트
  → POST gopang-proxy.tensor-city.workers.dev/ai/chat
     { provider: "deepseek", model: "deepseek-chat", system: SYS, messages: [...] }
  → Worker가 env.DEEPSEEK_API_KEY로 DeepSeek API 호출
  → 실패 시 env.ANTHROPIC_API_KEY로 Claude 폴백
  → { content: "..." } 반환
```

## 8. 보안 및 프라이버시

### 8.1 신원 보호

모든 사용자 식별은 고팡 IPv6 주소(`2601:xxxx:…`)로 이루어진다. 이름·전화번호·주민등록번호는 PDV 내부에 암호화 저장되며, 플랫폼 서버에 전달되지 않는다. 운전자 성명은 AI 응답에서 `성+○○` 형식으로 마스킹된다(예: 김○○).

### 8.2 API 키 보안

모든 외부 API 키(DeepSeek, Kakao, Supabase)는 Cloudflare Workers의 환경 변수(Secrets)로 관리되며, 클라이언트 코드에 직접 노출되지 않는다.

```
클라이언트 → gopang-proxy → 외부 API
           (CORS + 서버사이드 키 주입)
```

Cloudflare Dashboard 시크릿 목록:
- `DEEPSEEK_API_KEY`: DeepSeek V3 API
- `KAKAO_REST_KEY` / `KAKAO_JS_KEY`: Kakao Maps
- `SUPABASE_KEY`: PDV 로그 데이터베이스

### 8.3 PDV 무결성

각 PDV 레코드는 `content_hash`(SHA-256)를 포함한다. 분쟁 발생 시 해시 값으로 레코드 위변조 여부를 즉시 검증할 수 있다. Supabase `pdv_log` 테이블에는 `report_id` 기반 중복 방지 인덱스가 적용되어 있다.

### 8.4 긴급 상황 대응

긴급 신고 시 다음이 즉시 동작한다.

1. `PDV.writeEmergency()` 호출 → PDV에 긴급 기록 생성 (timestamp, 위치, 차량번호, 운전자 IPv6)
2. `recipients: ['gopang-pdv', '112']` 설정 → 112에 PDV 기록 자동 전달
3. 이 기록은 수정·삭제 불가 상태로 저장되어 법적 증거 효력을 가진다

## 11. 사용 시나리오

### 시나리오 1. 단거리 화물 배송 (L1~L2)

> 제주시 한경면 거주 농민이 감귤 1박스를 제주도청으로 보내고자 한다.

1. 농민이 webapp.html의 AI 채팅에 입력: *"한경면에서 제주도청으로 감귤 한 박스"*
2. AI가 수요를 파싱 (물류, 32km, L2 범위)하고 한경면 → 제주시 방향 차량을 탐색
3. 마침 한림읍 출발, 제주시청 방면 운행 중인 화물차 BB-042를 선정
4. 농민이 수락, 6 GDC 에스크로 예치
5. 운전자 BB-042에게 메시지 전송: *"한경면 청수리에서 감귤 1박스 수령 → 문연로 6 제주도청 전달, 보상 6 GDC"*
6. 운전자 수락, 경로 이탈 없이 수령·전달
7. 전달 완료 즉시 GDC 이체, 양측 PDV에 물류 완료 기록

### 시나리오 2. 장거리 릴레이 배송 (L4)

> 부산 해운대의 의류 업체가 서울 강남에 샘플 박스 3개를 당일 보내야 한다.

1. 업체 담당자가 desktop.html에서 입력: *"부산 해운대에서 서울 강남으로 의류 박스 3개"*
2. AI가 380km, L4 범위 판별, 경부고속도로 릴레이 구성 제안
3. 구간 A: BB-108 (부산해운대 → 천안삼거리휴게소, 28 GDC)
4. 구간 B: BB-247 (천안삼거리휴게소 → 서울강남, 17 GDC)
5. 담당자 수락, 총 45 GDC 에스크로
6. 두 차량이 천안삼거리휴게소에서 만나 인수인계
7. PDV에 각 구간 기록, 최종 전달 완료 후 GDC 분할 정산

### 시나리오 3. 긴급 안전 상황

> 탑승 중 이용자가 위험을 감지했다.

1. 앱의 🚨 긴급 버튼 터치
2. `PDV.writeEmergency()` 즉시 호출
3. 현재 위치, 차량번호, 운전자 IPv6가 PDV에 기록
4. 112 자동 연결, PDV 기록 전달
5. 해당 기록은 수정·삭제 불가 — 법적 증거 효력 발생

## 13. 용어 정리

| 용어 | 정의 |
|------|------|
| **고팡 (Gopang)** | K-Traffic이 속한 생태계. 고팡 ID, PDV, GDC, Openhash를 공통 인프라로 제공 |
| **고팡 블랙박스** | 등록 차량에 탑재되는 상시 가동 위치 전송 모듈. 1분 단위 데이터 전송 |
| **Openhash** | 고팡의 분산 네트워크 서버 클러스터. L1~L5 계층으로 교통 정보 전파 |
| **PDV** | Personal Data Vault. 이용자 본인이 소유하는 암호화 데이터 금고. 이동·거래·신원 기록 저장 |
| **GDC** | Gopang Digital Currency. 고팡 생태계 내부 통화. 1 GDC ≈ 1,000원 |
| **동선 겹침** | 차량의 예상 경로가 수요의 출발지 또는 목적지를 통과하는 상태 |
| **릴레이** | 장거리 수요를 2대 이상의 차량이 구간별로 나누어 처리하는 방식 |
| **인수인계 거점** | 릴레이 배송 시 차량 간 화물 또는 승객을 옮기는 중간 지점 (휴게소·터미널·물류센터) |
| **최소 전파** | 수요 동선 범위 내의 Openhash 계층에서만 탐색하고 상위 계층에 불필요한 데이터를 전달하지 않는 원칙 |
| **고팡 ID** | 고팡 사용자의 고유 식별자. IPv6 주소에 지역 코드가 인코딩되어 있음 |
| **L0~L3** | PDV 인증 레벨. L0=기기 인식, L1=실명, L2=생체, L3=시드 |
| **L1~L5** | Openhash 계층. L1=읍면동, L2=시군구, L3=광역시도, L4=국가, L5=글로벌 |
| **gopang-proxy** | Cloudflare Workers 기반 API 게이트웨이. API 키를 서버사이드에서 관리 |
| **DeepSeek V3** | K-Traffic AI 매칭 엔진. 수요 파싱, 차량 탐색, 릴레이 조합, 메시지 생성 담당 |
| **content_hash** | PDV 레코드의 SHA-256 해시. 위변조 감지에 사용 |
| **DM-XXXX** | 수요 ID. AI 매칭 엔진이 수요 발생 시 자동 부여 |
| **BB-XXX** | 블랙박스 차량 ID. Openhash 시스템 내 차량 식별자 |
| **SSO** | Single Sign-On. 고팡 ID 하나로 모든 서브시스템에 자동 로그인 |
| **GWP 토큰** | Gopang Web Portal 토큰. SSO 인증 후 서브시스템에 전달되는 단기 토큰 |
